# UniVMS — notes for Claude Code (read first)

This file is the project's memory: conventions, what exists, what was learned, what the user wants. Update it with every change (the user works from more than one PC and relies on it).

## What this is

Electron desktop VMS client (iVMS-4200 replacement) for **Hikvision** NVR/DVR/IPC via ISAPI and **DW Spectrum** (Nx Witness based) servers. Ships as Windows NSIS installer + portable exe, Debian `.deb`, RPM `.rpm`, each with a bundled static ffmpeg. GitHub: `gxmonto/univms` (**public** since 2026-10-02 so auto-update works without tokens). SDK runtime lives in the private `gxmonto/univms-assets` repo (release `hiksdk-v6.1.9.4`); CI reads it with the `ASSETS_TOKEN` secret (fine-grained PAT, Contents: read-only on univms-assets). Never put the SDK or device credentials in the public repo. Owner: Mike (SightWatch, `mike@sightwatch.com`), gh CLI logged in as `gxmonto`.

## Versioning (user's rule — NOT textbook semver)

Version is `1.X.Y`.
- **Major change** → bump the **second** number, reset the third: `npm run release:major` (1.2.3 → 1.3.0). Use for a genuinely new capability (new module/feature area, new vendor, packaging/update-mechanism changes).
- **Minor change** → bump the **third** number: `npm run release:minor` (1.2.3 → 1.2.4). Use for fixes, small enhancements, UI tweaks, dependency bumps.
- The first number stays `1` unless the user asks.
- **Release rarely.** On 2026-10-02 the user reset the version to 1.0.0 after ten releases in a few hours ("treat them as test releases"). Do not cut a release after every fix: batch work under *Unreleased*, release only when the user asks or when a work session is wrapped up, and ask before releasing if unsure. Local smoke/e2e runs and `dist/win-unpacked` are the way to test, not GitHub releases.
- **Judge the size of the whole change set before bumping** (user feedback after 1.1.0). A round of fixes is minor even if there are many of them; when a round mixes fixes with a real new feature, say which bump you chose and why. When unsure, ask.
- Keep notes under `## Unreleased` in `CHANGELOG.md` for every change; the release script moves them under the new version, writes `release-notes.md`, commits `Release vX.Y.Z`, tags, and with `-- --push` pushes (tag triggers `.github/workflows/release.yml`, which builds all installers and publishes the GitHub release with that section as notes). Do **not** put versioning explanations in README/CHANGELOG — they are for users; this file is for Claude.

## How things work (decisions)

- Video: ffmpeg remuxes RTSP to fragmented MP4 (`-movflags empty_moov+default_base_moof+frag_keyframe -frag_duration 300000`), piped over IPC, played with MSE. H.265 → MSE codec check → automatic transcode restart. No `-tag:v hvc1` (breaks H.264).
- Hikvision has two connection types (`device.transport`): `isapi` (HTTP/ISAPI on the web port, default) and `sdk` (Hikvision Device Network SDK on the server port 8000, like iVMS-4200). RTSP port is auto-read from `/ISAPI/Security/adminAccesses` in ISAPI mode.
- **Hikvision SDK path** (`src/main/hiksdk.js`, koffi FFI, no compiler): `HikSdkSession` per device — login (`NET_DVR_Login_V40`), ISAPI pass-through (`NET_DVR_STDXMLConfig`, so the whole ISAPI driver works unchanged over 8000), live (`NET_DVR_RealPlay_V40` + `NET_DVR_SetStandardDataCallBack` → PS stream piped into ffmpeg stdin via `streams.startPiped`), playback (`NET_DVR_PlayBackByTime_V40`, device **local** time), snapshots (`NET_DVR_CaptureJPEGPicture_NEW`), voice (`NET_DVR_StartVoiceCom_MR_V30`, G.711 only; voice channel = `byStartDTalkChan + ch − 1` for IP cameras, 1 = recorder output), alarms (`NET_DVR_SetupAlarmChan_V50`, decodes `COMM_ALARM_V30`, maps `COMM_ALARM_RULE`). SDK channel numbers: IP camera N = `byStartDChan + N − 1`. Struct layouts use default alignment (koffi sizes verified in `tests/hiksdk.test.js`). The libraries (~45 MB win, ~20 MB linux) are downloaded by `scripts/fetch-hiksdk.js` from hikvision.com (needs a browser User-Agent; URLs are stable per SDK version) into `vendor/hiksdk/<platform>-x64` and bundled as `resources/hiksdk`; not in git. hikvision.com's CDN blocks GitHub runner IPs with a bot-check page, so the pruned runtimes are stored as assets of release `hiksdk-v6.1.9.4` in the private `gxmonto/univms-assets` repo (`hiksdk-win32-x64.zip`, `hiksdk-linux-x64.zip`); `fetch-hiksdk.js` tries that first (token from `ASSETS_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`) and falls back to the CDN; locally a missing SDK is a warning, in CI `UNIVMS_HIKSDK_REQUIRED=1` makes it fatal. To update the SDK: download the new zips here, run the fetch script against them, zip the pruned folders and `gh release create hiksdk-vX.Y.Z …`, then bump `ASSET_TAG`/`VERSION` in the script. **Not yet tested against a real NVR** — needs one reachable on port 8000.
- **Dahua** (`src/main/dahua.js`, type `dahua`, also Amcrest/Lorex/IC Realtime OEMs): digest HTTP CGI, `key=value` responses parsed by `parseKv`/`rows`. Channels from `configManager.cgi?name=ChannelTitle` (index i → channel i+1; `mediaFileFind` conditions are 0-based), online state from `LogicDeviceManager.cgi?action=getCameraState`, codecs from `name=Encode`. RTSP `/cam/realmonitor?channel=N&subtype=0|1`, playback `/cam/playback?channel=N&starttime=YYYY_MM_DD_HH_MM_SS&endtime=…` (device local time), RTSP port from `name=RTSP`. PTZ `ptz.cgi?action=start|stop&code=…` (speed 1–8, stop needs a code → last code remembered). Events: `eventManager.cgi?action=attach&codes=[All]` multipart stream (`Code=…;action=Start|Stop;index=N;data={…}`), handled by the hub's `_hikLoop` (any driver with `alertStream`). Verified 2026-10-19 on an EV-N42A16P16 NVR (37-16 Union St): `getCameraState` is **501** there → fallback `LogicDeviceManager.cgi?action=getCameraAll` where `camera[i].UniqueChannel` is the recorder slot (0-based) and `Enable`/`DeviceInfo.Enable` whether a camera is attached (`Channel` is the camera's own input, always 0); `mediaFileFind` `condition.Channel` is **1-based** on that firmware (0 → HTTP 400); storage `list.info[0].Detail[k]` = partitions, summed. Mock test `tests/dahua.test.js` mirrors these. Vendor labels: Hikvision type = Hikvision/LTS/ENS (Hikvision OEM); DW Spectrum type = Nx Witness and Wisenet WAVE (verified 2026-10-20: 1455 Rt 32 WAVE 6.0.4 works with the DW driver, REST mode, 8 cameras). Lorex (N882A6, http 7005) and Amcrest (NV5216, http 37776) verified with the Dahua driver. **INVID Elevate/Paramont are NOT Hikvision OEM**: TVT-made recorders (server port 6036, web `/doLogin` XML API, no ISAPI/LAPI/Dahua/SUNAPI endpoints) — pending, see below.

Verified 2026-10-19 on NVR302/304/504: `System/DeviceInfo`, `Channels/System/ChannelDetailInfos` (ID 1-based, `Status` 1 = online), snapshot `Channels/{N}/Media/Video/Streams/0/Snapshot`, recordings `…/Streams/0/Records?Begin=&End=` (epoch s; `RecordType` 4 treated as motion), `System/Time`, `PTZ/Capabilities`+`PTZ/Presets`. RTSP live `/unicast/c{N}/s{0|1}/live` (NVR), `/media/video{1|2}` (camera), playback `/unicast/c{N}/s0/playback?begin=YYYYMMDDHHMMSS&end=…` (verified, `/c1/b…/e…/replay/` is 404). No event endpoint (push subscription only) → no events; PTZ control not implemented (no PTZ unit to verify). RTSP port is not readable through LAPI → device field (default 554).

- **Reolink UID playback through Reolink's own SDK (2026-10-21)** — `src/main/reolinksdk.js` (one file: main-side proxy + host in an Electron `utilityProcess`, same pattern as the Hikvision SDK host; `inProcess()` for Node harnesses). Loads `libBCSDKWrapper.dll` from the user's installed Reolink desktop app (`%LOCALAPPDATA%\Programs\Reolink\resources\app`, override `REOLINK_APP_DIR`); proprietary, **never bundled**. Signatures/structs were read from the Reolink app's own node-ffi table (`resources/app/183.js`: ffi table in module 35490, struct types in module 39889, size constants in module 22141; command IDs `E_BC_CMD_*` in the same bundle — LOGIN 2087, REALPLAY 2089, SEARCH_RECFILES 2113, DOWNLOAD_CUT 2145, DOWNLOAD_CUT_PROGRESS 2148). Flow: `BCSDK_Open({0,0,0})` → `BCSDK_AddDevice(LoginInfo{iAuthMode 0, port 9000, uidPort 2018, uid, user, pass}, Callbacks{func, jsonApiEnable 0})` → `BCSDK_DeviceForceOpen(h, {async:true})` → wait event 2087 rsp 0 (≈1.5 s over the relay, vs ≈10 s for Neolink). Search: `BCSDK_RecordFilesSearch(h, ch, SearchParam{logicChnBitmap 255, remoteChn -1, bsearchAITrack true, seq})`, results arrive as event 2113 with `{seq, fileNum, fileType, streamType, recFile[40]}` batches (fewer than 40 = last). Download: `BCSDK_StartDownloadByTime(h, ch, "", 0, start, end, stream, tmpDir, dst, 0)` (PC-local date parts), event 2145 = transfer done, then **`BCSDK_StopDownload` is what finalizes/moves the MP4** (the Reolink app does it at 100 %); ≈4 s per minute of sub stream (≈15× real time); clips start at the keyframe before the requested time (+0–2 s overlap). The driver's `playbackPiped` downloads 30 s first then 2-min chunks (prefetched, ≤3 min ahead of real time, one retry each), remuxes each to MPEG-TS with `-output_ts_offset (from-start)` and feeds `streams.startPiped(..., {format:'mpegts'})` via the `stream:start` branch for `driver.playbackPiped`. **Live view stays on Neolink**: the SDK's live frame callback only gets decoded keyframes (YUV in an AVFrame: `plane[].address` → `data[0..2]` pointers + `linesize` at +64; needs `SetUseHardwareDecoder(false)` and a non-null user-data block) — full-motion video goes to its native window player. koffi gotcha: never make two `koffi.view` ArrayBuffers over the same native memory (V8 aborts, exit 134); copy with `msvcrt!memcpy` instead. Idle SDK sessions log out after 2 min (NVR session cap). Verified on 101 Franklin (search + playback on ch 0–2; ch 1 sub is H.265).

App-like test (gaps harness): first output 11–12 s, longest gap 1.6–3.8 s (was 15–20 s). The user's PC runs a full-tunnel OpenVPN (routes 0.0.0.0/1 + 128.0.0.0/1 via 192.168.1.1, PC 192.168.1.6) — relay traffic goes through it; the VPN's 192.168.1.x is NOT the recorder's LAN (192.168.1.141 unreachable).
- **Reolink UID bursts/reloads (2026-10-21, Neolink build 8 `neolink-v0.6.3-univms8`)**: user saw tiles play then reload. Cause 1 (fork): `send_to_appsrc` paused the appsrc until 2/3 of `buffer_size(bitrate)` was queued and resumed/paused around 1/3–2/3 — with the 4 Mbit/s fallback bitrate that is ~700 kB ≈ 17 s at ~40 kB/s per camera → removed (live sources never pause). Cause 2 (physics): measured relay throughput at 101 Franklin ≈ 230 kbit/s for one sub stream, ≈ 580 kbit/s for one 4K main → total cap ≈ 0.5–0.6 Mbit/s; 10 sub streams need ≈ 2.3 Mbit/s, so the NVR sends bursts with 10–20 s gaps (keyframes ~20 s apart). App: UID live ffmpeg uses `frag_every_frame` (`opts.fastProbe`) so frames reach the player as they arrive, and UID tiles tolerate 45 s without data before reconnecting (`Player opts.stallSeconds`, live.js; default 12 s). Test harness `scratchpad/bcsdk/gaps` (Electron, real driver, streams.js args; env CHS, STREAM, MOV, RUN_S) reports first output and longest gap per camera.
- **Reolink UID start-up time (2026-10-21, Neolink build 7 `neolink-v0.6.3-univms7`)**: cold start with 10 cameras went from ~30 s + retries (tiles opened before Neolink had the channel → no splash → error → player backoff up to 24 s) to ~15–19 s. - **Reolink UID shared login, round 2 (2026-10-21, Neolink build 5 `neolink-v0.6.3-univms5`, verified with a 24-channel stress test)**: user's 1.4.2 opened 24 tiles at once → Neolink 1.3 GB, RTSP server stopped answering DESCRIBE. - **Reolink via UID** (`src/main/reolinkuid.js`, type `reolinkuid`, helper `src/main/neolink.js`): for sites that only work through the Reolink app (101 Franklin: all ports closed, UID in the sheet/dashboard). ## Gotchas learned

- **Hikvision locks the account after a few failed logins** (ISAPI `userCheck` returns 401 with `lockStatus lock` and `unlockTime`; SDK code 153). Background retries (health check every 60 s, alarm resubscribe backoff) turned one bad login into a permanent lock in 1.3.0. Rule now: after any auth failure (`HttpError.authFailure`, `SdkError.authFailure`) the hub blocks automatic logins to that device until it is edited (`status.authFailed`, `authBlocked()`), and the SDK does a TCP connect test before sending credentials. Remote sites often forward only HTTP (e.g. `:9000`) and RTSP `:554`, not the server port 8000 → SDK mode cannot work there; use ISAPI.
- Switching a device to SDK must force port 8000 (the dialog now does); the first field test sent SDK logins to the HTTP port 9000.
- Config saves failed silently on the user's installed 1.3.0 (file untouched while devices were added). **Cause found 2026-10-02**: copies started by double-click (no console) wrote neither the log nor the config, while shell-started smoke runs did — `console.log` in a console-less Windows GUI process can throw (stdout is not writable) and the exception aborted the callers. `main.js` now wraps every console method in try/catch, ignores stdout/stderr errors and writes `userData/logs/main.log` *before* echoing to the console. Diagnose with a detached launch (`Start-Process` from PowerShell) and compare the log size before/after; `store.flush()` also toasts errors and Settings → About shows the last save time.
- **Do not store secrets with Electron `safeStorage` alone on Windows.** It encrypts with a per-profile AES key that Chromium keeps in `userData/Local State` and writes lazily; when the app is killed (Stop-Process, crash, `app.exit`) before that flush, the next start generates a *new* key and every `enc:` value fails with "Error while decrypting the ciphertext provided to safeStorage.decryptString". The store then returned '' and the app logged in with empty passwords → Hikvision lockouts (part of the "sdk never connects"/lockout saga). Now `src/main/secrets.js` keeps a random 256-bit key in `userData/univms.key`, protected with DPAPI through koffi (`crypt32!CryptProtectData`, `UNIVMS_DATA_BLOB` struct), falling back to safeStorage (Linux keyring) or plain; passwords are `aes:` (AES-256-GCM). Legacy `enc:` values are migrated when they still decrypt; otherwise `getDeviceWithSecret().secretLost = true`, `DriverPool.get` throws an `authFailure` error (no login attempt at all) and the devices table shows "Saved password unreadable — edit the device and enter it again". The user's "260 e 72nd" device needs its password re-entered once.
- Windows Error Reporting writes `%LOCALAPPDATA%\CrashDumps\UniVMS.exe.<pid>.dmp` when a UniVMS process crashes; cause confirmed: `app.exit()` (smoke/e2e paths) does not emit `will-quit`, so the packaged process exited with the Hikvision SDK still initialized and segfaulted during teardown (exit 139, new dump each run; normal window-close quit was fine). `ctx.shutdownAll()` (config flush first, then updater/hub/streams/SDK, each in its own try/catch) now runs on `will-quit` *and* before every `app.exit()`; verified: packaged smoke exits 0 with no new dump. A crashed renderer (log line `renderer gone crashed`) is reloaded automatically (max 3 per minute).
- 2026-10-07 report from the user's **other PC** (installed v1.0.0): all three devices "Login rejected" (SDK 153 locked / 401 / SDK code 1) although passwords were unchanged — that is the safeStorage key loss above, still shipping in v1.0.0; the fix is unreleased. After the update those devices show "Saved password unreadable" and need the password re-entered once. Same report: "uninstalled, config stayed" → `nsis.deleteAppDataOnUninstall: true` (electron-builder's uninstaller skips the deletion when running as an update, `isUpdated`).
- `#nav` must NOT be `-webkit-app-region: no-drag` (it stretches with `flex: 1`, so the empty stretch of the title bar became dead space); only the buttons are no-drag via `#topbar button`.
- Single-instance lock: a second UniVMS.exe (e.g. from `dist-test`) silently exits when another copy (e.g. `dist\win-unpacked` started hours earlier) is running — check `tasklist | findstr UniVMS` when "it does not open".

- `el('div', { draggable: true })` must emit `draggable="true"`; an empty attribute disables dragging (this broke all drag & drop in 1.0.0).
- Node ≥16: a server request's `'close'` fires when the body is consumed — use `res.on('close')` for connection lifetime (mock event stream bug).
- ffmpeg cannot serve RTSP for players (`-rtsp_flags listen` only accepts pushes); use mediamtx for tests.
- Windows: Git's GNU `tar` misreads `C:\…` paths; `scripts/fetch-ffmpeg.js` uses `System32\tar.exe`. Python 3.14 refuses paths > 260 chars — copy scripts to a short path. GitHub downloads here are slow (~200 KB/s) and reset; archives are cached in `vendor/ffmpeg/.cache/`.
- CRLF: the repo has `.gitattributes` `* text=auto eol=lf`; `core.autocrlf=false` locally. All changelog tooling normalizes `\r\n` (the 1.1.0 release had its changelog mangled by CRLF).
- Electron pinned to 33.x (runtime zip was cached locally). electron-builder `publish` config is required for `latest.yml`; CI passes `--publish never` and uploads artifacts itself.
- Mutation Events (`DOMNodeRemoved`) are gone in Chromium ≥127 → use modal `onClose`.
- `#app` must use `grid-template-columns: minmax(0, 1fr)`: an implicit `auto` column is sized to the top bar's min-content width and the whole UI overflows the window (the user's "icons hidden" report). Module bar uses short names (`short` in `VIEWS`) so it fits at the default width next to the window controls.
- ISAPI `audioSamplingRate` is in kHz ("8"). `talk.js` still uses ScriptProcessorNode (deprecated but working); AudioWorklet is the eventual replacement. A synthetic `.click()` is not a user gesture → always `audioContext.resume()`.
- Hikvision snapshot endpoint is not in the mock, so the rules editor shows a black background in e2e; on real devices the snapshot loads.
- WSL on this PC has no outbound network and `sudo` needs a password (`wsl -u root` works) — Linux packages are built on Windows with nfpm instead.
